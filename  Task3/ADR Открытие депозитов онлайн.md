# Открытие депозитов онлайн MVP ADR

### **Название задачи:**

MVP цифрового открытия депозитов через интернет-банк и сайт

### **Автор:**

Команда цифровой трансформации

### **Дата:**

27 марта 2025

### **Функциональные требования**


| **№** | **Действующие лица или системы** | **Use Case**                                                                 | **Описание**                                                                                                                                |
| :----: | :-------------------------------------------------------- | :--------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------- |
|   1   | Клиент (интернет-банк)                  | Подача заявки на депозит                                | Клиент указывает параметры вклада, заявка направляется в микросервис депозитов |
|   2   | Клиент (сайт)                                   | Подача заявки на депозит                                | Клиент вводит ФИО и телефон, данные отправляются в микросервис депозитов              |
|   3   | Микросервис депозитов                 | Передача заявок                                                | Маршрутизирует заявки в систему кол-центра или в АБС при необходимости                  |
|   4   | Кол-центр                                         | Обработка заявки                                              | Менеджер получает заявку, связывается с клиентом для согласования условий           |
|   5   | Менеджер бэк-офиса                        | Подтверждение заявки в АБС                            | Вносит депозит вручную после согласования условий                                                       |
|   6   | АБС                                                    | Создание депозита и отправка уведомления | Создаёт депозит, инициирует отправку СМС через шлюз                                                     |

### **Нефункциональные требования**


| **№** | **Требование**                                                                                                                                  |
| :----: | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
|   1   | Интерфейс в ИБ и на сайте должен соответствовать брендбуку и дизайн-системе               |
|   2   | Время отклика < 1 сек при взаимодействии пользователя с ИБ или сайтом                             |
|   3   | Доступность систем 99.9%, включая интернет-банк и микросервис депозитов                          |
|   4   | АБС не должна перегружаться — запрещена прямая интеграция из ИБ                                     |
|   5   | Данные клиента и операций должны шифроваться (TLS)                                                                 |
|   6   | Используются существующие технологии (MS SQL, Oracle, .NET Framework, PL/SQL)                                           |
|   7   | Возможность горизонтального масштабирования интернет-банка и нового микросервиса |
|   8   | Поддержка интеграции с действующим СМС-шлюзом                                                                     |
|   9   | Централизация логики ставок и заявок в новом микросервисе                                               |
|   10   | Реализация без доработки ядра интернет-банка подрядчика                                                  |

### **Решение**

Реализация нового микросервиса "Депозиты", который служит центральным элементом взаимодействия всех систем в MVP. Клиенты подают заявки через интернет-банк или сайт, которые направляют данные в микросервис. Он маршрутизирует заявки: для новых клиентов — в систему кол-центра, для существующих — в АБС (в ручной обработке менеджером).

Как работает сейчас

* Ставки рассчитываются вручную в Excel
* Участвуют сотрудники бэк-офиса депозитов и кредитов
* Обмениваются файлами по почте
* Ставки не централизованы и недоступны в системах в реальном времени

Целевое решение для MVP (упрощенное):

1. Централизовать хранение ставок в **микросервисе депозитов**

Создаётся отдельная таблица в БД микросервиса:

```
DepositRates (
id,
productType,
minAmount,
maxAmount,
baseRate,
bonusRateConditions,
effectiveDate,
isActive,
segment (e.g. VIP, pensioner),
updatedBy
)
```

2. Потоки работы со ставками
   2.1. **Сотрудник бэк-офиса**:

   - Заходит в **внутреннюю админку микросервиса депозитов** (SPA на React + API)
   - Заполняет или редактирует ставки (на основе данных из Excel)
   - Сохраняет — данные пишутся в БД микросервиса
   - Можно добавить **роли/права** (например, кредиты не могут редактировать депозиты и наоборот)

   2.2. **Сотрудник в отделении (фронт-офис)**:

   - При оформлении заявки в АБС (или в новом UI, если будет) — видит **актуальные ставки**, полученные через API от микросервиса
   - Больше **не пишет письма**, не ждёт согласования.

   2.3. **Клиент (через интернет-банк)**:
   Получает:

   - **Базовые ставки** — если нет авторизации
   - **Персонализированные ставки** — если вошёл в ИБ (по сегменту, профилю клиента и пр.)

   Логикка может быть такая:

   - Клиент заходит в ИБ
   - Backend интернет-банка вызывает API микросервиса `/rates?clientId=...`
   - Сервис возвращает ставки по правилам (например):
     Если у клиента вклад > 1 млн — добавляется надбавка
     Если клиент пенсионер — другая сетка ставок
     Если VIP — можно вытащить спецставки

   2.4. Сотрудники call-центра

   - Через REST API делают `GET /rates`
   - Видят ставки, которые можно озвучивать клиенту
   - Партнёрский КЦ получает эти же ставки **в виде файла (CSV)**
3. Безопасность и контроль

   * Все ставки логируются (`updatedBy`, `timestamp`)
   * Можно предусмотреть предварительную **модерацию** ставок (через статус: draft → active)
   * Ставки не записываются напрямую в АБС

   Итог: Как сервис депозитов получает и отдает ставки


   | Источник / получатель | Как работает                                                                             |
   | --------------------------------------- | --------------------------------------------------------------------------------------------------- |
   | **Бэк-офис**                     | Через админку микросервиса вручную вносит ставки         |
   | **Клиент (ИБ/сайт)**        | Получает через API — или общие, или персонализированные |
   | **Отделения банка**       | Получают через интерфейс, интегрированный с API               |
   | **Кол-центр**                   | REST API для получения ставок                                                     |
   | **Партнёрский КЦ**         | Файл ставок (CSV/XLSX), выгружаемый из микросервиса              |

#### Диаграмма контекста (C4) ContextDiagram.drawio

* **Клиент** → **Интернет-банк**/**Сайт** → **Микросервис депозитов**
* **Микросервис депозитов** → **Кол-центр** → **Менеджер**
* **Микросервис депозитов** → **АБС** (ручная обработка) → **СМС-шлюз** → **Клиент**

#### Диаграмма контейнеров (C4) ContainerDiagram.drawio

* **Интернет-банк** (ASP.NET MVC 4.5, MS SQL)
  * Подключается к микросервису по API
* **Сайт** (React + PHP)
  * POST-заявки в микросервис
* **Микросервис депозитов** (новый сервис)
  * .NET 6+, API + интеграции
  * БД: Oracle или MS SQL
* **Кол-центр** (React + Java Spring Boot + PostgreSQL)
* **АБС** (Delphi клиент, PL/SQL + Oracle)
* **СМС-шлюз** — подключается к АБС или микросервису

**Решения и принципы:**

* Интернет-банк не должен напрямую обращаться к АБС
* Новый сервис содержит бизнес-логику, маршрутизацию, централизованные ставки
* Системы связаны API-интеграциями (без прямого доступа к БД)
* Масштабируемость и отказоустойчивость достигается за счёт разделения обязанностей

### **Альтернативы**

* Встраивание бизнес-логики в интернет-банк (жёсткая зависимость от подрядчика)
* Расширение АБС (против: риски производительности и отказов)

**Недостатки, ограничения, риски**

* Микросервис требует поддержки и дополнительной инфраструктуры
* Данные по ставкам пока ведутся вручную и требуют централизации
* АБС перегружена — необходимо контролировать нагрузку и режимы доступа
* MVP включает ручную обработку, без полной автоматизации
* Возможны задержки при подтверждении заявок, особенно с участием кол-центра
